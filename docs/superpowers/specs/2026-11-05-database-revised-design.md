# Restaurant database - revised logical design

Date: 2026-11-05. Status: REVIEW PROPOSAL, not an approved migration.
Supersedes conflicting database proposals in chat, not the approved MVP scope.
Sources: restaurant-mvp-scope, existing business/technology specs, existing
database design, report v2.1 handoff, actual IdentityDbContext.

## 1. Decisions and corrections

- One SQL Server database, ten module schemas and independent DbContexts.
- Physical foreign keys inside a module; cross-module references are logical.
  These do NOT provide database-enforced referential integrity. Module contracts,
  transactional validation and reconciliation are mandatory compensating controls.
- Actual IdentityDbContext uses IdentityUser<Guid>/IdentityRole<Guid>. Keep this:
  identity IDs and every user/role reference are uniqueidentifier, NOT bigint.
- Other entity IDs: bigint IDENTITY. Join tables use composite primary keys.
- Keep one ChiTietDon per ordered portion, matching the existing design. Do not
  add quantity-based completion/delivery tables on top of this representation.
- Topping and ordinary options share TuyChon; NhomTuyChon.Loai distinguishes
  TOPPING from TUY_CHON. A topping is NOT an option group.
- Remove PhanBoThanhToan and DongHoanTien. Every payment has one invoice;
  refunds refer to one original payment and an amount, never selected dishes.
- No recipes, stock reservation, per-dish stock deductions, attendance, payroll,
  cards, public registration, closed-day reopening or automatic late-food alerts.

## 2. Column notation and conventions

PK primary key; FK physical reference; REF logical cross-module reference;
UQ unique; ? nullable; RV rowversion. Unless marked ?, columns are NOT NULL.
All entity tables have Id PK unless a composite PK is explicitly specified.
Codes/statuses varchar(32), names nvarchar(150), reasons nvarchar(1000),
notes nvarchar(2000), timestamps datetime2(7) UTC, dates date, flags bit.
Business money decimal(18,0); stock quantity decimal(18,4); conversion factor
decimal(18,6); internal valuation decimal(28,8), round only at reporting boundary.
Positive transaction money > 0; price/opening cash >= 0. Signed adjustments,
profit, net receipts and cash variance must permit negative values.
New mutable aggregates have RV. Identity uses its existing concurrency/security
stamps. Immutable detail/history tables do not need RV.
Never cascade-delete financial/operational history. NO ACTION on business FKs.
Every FK and hot logical reference gets an index unless covered by an existing
index prefix. UQ constraints below must be implemented, not just described.
Common operational metadata: TaoLuc, NguoiTaoId REF identity.NguoiDung.
Snapshots are deliberate historical denormalization, not live catalog lookups.

C01 PROPOSAL, approval needed: obligation = sum(original lines) + sum(signed
obligation adjustments) - sum(waivers), never negative. Net collected = successful
payments - successful refunds. Due = max(obligation-net collected,0).
Refundable excess = max(net collected-obligation,0). An amount refund does not
automatically cancel a dish or zero its price. The manager records an independent
obligation reduction when the customer no longer owes the refunded amount.
Waivers cover outstanding debt only, not already-collected money.

Refund holds: reserve capacity at DA_DUYET; retain at DANG_CHI/CHO_DOI_SOAT.
Per-payment successful refunds + active holds <= original successful payment.
Per-invoice refunds also cannot exceed refundable excess after other holds.
Lock invoice first, then affected payments in ascending ID order for all commands.
Unknown payout stays CHO_DOI_SOAT; never create a second payout blindly.
Closed original day stays unchanged; current-day corrections/refunds reference
the original invoice/payment and affect current-day movement reporting.

C02 proposal formula, under close-day freeze:
Q = opening quantity + effective purchases + signed quantity adjustments.
V = opening value + purchase value + signed value adjustments.
Require Q >= approved count >= 0 and V >= 0.
If Q > 0: average = V/Q; closing value = count*average;
usage = Q-count; cost = V-closing value using high internal precision.
If Q=0 require count=0 AND V=0; otherwise require explicit correction, not
silent residual write-off. Carry internal closing value to the next day.
Expense-on-purchase ingredients: cost = effective purchase values; no stock count.
Round aggregate VND once consistently; persist rounding difference in day snapshot.
Inventory usage includes waste/unexplained usage: this is not recipe-level COGS.

## 4. Cross-module relationship register

Notation: parent -> children, cardinalities relative to one parent.

| Parent | Child | Cardinality | Enforcement |
|---|---|---|---|
| identity user | operational creator/approver | 1 : 0..N | REF; valid actor contract; no user hard delete |
| salesday day | sessions/orders/payments/refunds/counts | 1 : 0..N | REF; day gate; posting-day validation |
| seating session | sales order | 1 : 0..N | REF; same day; dine-in only |
| seating guest grant | sales batch | 1 : 0..N | REF; same session as target order |
| catalog variant | sales portion | 1 : 0..N | REF; variant belongs to selected item |
| catalog option | selected snapshot | 1 : 0..N | REF; group assigned to selected item |
| sales portion | fulfillment ticket | 1 : 0..N | REF; zero before confirmation; attempts unique |
| sales order | billing invoice | 1 : 0..1 | REF; UNIQUE invoice order reference |
| sales portion | invoice line | 1 : 0..1 | REF; UNIQUE portion reference |
| fulfillment incident | obligation adjustment | 1 : 0..N | REF; correlation/idempotency prevents duplicate effect |

Optionality matters: an unconfirmed portion has no ticket or invoice line.
An invoice line's portion must belong to that invoice's order, checked through
Sales contract in the same write boundary; two individually valid IDs are not enough.
No billing stock FK, no menu-to-ingredient recipe relation, no guest user account.

## 5. Transactions, lifecycle and integrity

C03 PROPOSAL: every day-scoped writer takes the SAME transaction-owned SQL
application lock for that day in Shared mode BEFORE reading day state. Closing
takes Exclusive mode and waits for previous writers, then changes DANG_BAN to
CHO_CHOT. Shared writers subsequently see CHO_CHOT and reject changes.
Use one common lock order: day gate, order/session, invoice, payments, stock IDs.
Never rely on a pre-transaction day-status check.

In CHO_CHOT allow read/validation only; cancelling close atomically returns to
DANG_BAN with audit, no published snapshot. Corrections/count entry happen after
cancel, not during freeze. Repeated close with same key returns prior result.
Check no open orders/sessions, unconfirmed batches, pending fulfillment effects,
unapproved counts, unresolved transfers/refunds or in-flight accounting events.
The command caller identity/permission and all quantities are revalidated.

Finalize counts, financial/stock snapshots, Outbox and DA_CHOT in one local
SQL transaction. Contexts must share DbConnection/DbTransaction and use their
own module APIs; do not query another module's entities directly. If workers
run on another connection, they do not join this transaction automatically.
Configure retry execution strategy around the entire transaction and reuse
idempotency key. No external bank/R2/SignalR calls inside database transaction.

Cross-module synchronous critical writes: confirm batch + invoice charge;
approve financial incident + obligation effect; close order + financial check;
close session + no open orders; close day + snapshots. Use module contracts
enlisted in shared transaction, or explicit durable pending states. Pure async
dispatch cannot claim atomic billing/closing without such coordination.

All state transitions use expected state/RV and validate authority. Timestamp and
actor pairs must be both NULL or both set. Successful transfers require manual
confirmation; successful refunds require approval and payout evidence. Never
update original successful money amounts; corrections are new audited entries.

Order close: portions reach accepted final states, no pending batch/incident,
receivable=0, refundable excess=0, no unresolved payment/refund. Session close:
all orders terminal, revoke guest grants. A zero-value order needs no zero payment.

## 6. Technical persistence and indexes

- Outbox per publishing module: Id Guid PK, AggregateId, AggregateVersion,
  Type, Payload, OccurredAt, ProcessedAt?, Attempts, NextAttemptAt?, LeaseUntil?,
  LastError?. Unique aggregate/version/event where appropriate. Audit/Identity
  also require durable audit delivery if written asynchronously; do not assume
  only the old seven modules can publish.
- Inbox per consuming module: PK(Consumer,EventId), ProcessedAt; processed
  marker and domain effect commit together. SignalR may duplicate; UI deduplicates.
- YeuCauDaXuLy per command-owning module: PK(Operation,ActorScope,Key),
  RequestHash, ResultReference, State, CreatedAt. Different payload with same
  idempotency key is rejected. Never permanently cache raw guest tokens/passwords.
- Hangfire owns technical tables in its own schema. Per-module migration history
  follows current infrastructure. No DB table for client audio playback needed.
- Hot indexes: batch(order,status); portions(batch); ticket(station,status);
  incidents(status); payment(day,status,method); refund(day,status);
  purchase(day,status); count(day,ingredient) UQ; audit(subject,time);
  outbox pending(NextAttemptAt,Id) filtered on ProcessedAt IS NULL.
- Card, item-refund and multi-invoice allocation tables MUST NOT reappear.

## 7. Relationship verification and acceptance matrix

Static review performed against sources and current scaffold; no live SQL Server
migration or concurrent integration test has been run. The following are required
tests, not claimed passing results:

1. Reject duplicate user role, username, invoice/order and line/portion mappings.
2. Reject mismatched variant/item, option/group/item and invoice-line/order.
3. Two concurrent opens/transfers cannot occupy the same table twice.
4. QR locator alone cannot order; expired/revoked grant and cross-session order fail.
5. Repeated batch confirmation creates one financial charge and one initial ticket.
6. Remake requires approved same-portion incident and creates no new revenue.
7. A portion/attempt cannot be served twice or after cancellation/replacement.
8. Two collectors cannot overcollect the invoice under the chosen no-overpay rule.
9. Concurrent refunds cannot exceed original receipt or invoice excess; unknown
   payouts retain holds and cannot be blindly retried.
10. Refund old sale posts to current day; original closed snapshot unchanged.
11. Purchase conversion edits do not alter historical quantity/value snapshots.
12. Archived stocked ingredient remains countable; invalid mode/unit change blocked.
13. Zero quantity/nonzero value prevents closing; signed adjustment included in cost.
14. Two closers produce one snapshot; late writer waits then fails on frozen state.
15. Rollback during close leaves no partial stock/report/financial finalization.
16. Negative daily net movement/profit is representable; units not mixed.
17. Account role revocation takes effect for active tokens per session policy.

## 8. Remaining approval gates

C01: obligation reductions, waiver/refund semantics and closed-invoice corrections.
C02: signed adjustment valuation, internal precision and rounding treatment.
C03: shared day-lock protocol, freeze/cancel and atomic transaction coordination.
C04: archive/mode changes while stock exists.
C05: guest grant stays valid within transferred session; current serving location.
C06: revenue measure versus cash movement for gross profit and closed snapshots.
Additional explicit MVP defaults: one open order/session; one selection of each
option/portion; price-change confirmation; no overcollection. These are proposals,
not implied approvals. Migration readiness requires approval, physical DDL with
named constraints/indexes, seeded permissions and execution of the test matrix.
